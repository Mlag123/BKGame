# BKGame: как структурировать проект (гайд для новичка)

Этот документ — практическая схема, как организовать код движка/игры, чтобы:
- было понятно, где что лежит;
- было легко добавлять новые фичи;
- можно было создать новый игровой объект через наследование от базового `SceneObject`.

---

## 1) Главная идея: разделяй **данные**, **поведение**, **рендер**

Частая ошибка новичков — один класс делает всё сразу: и хранит позицию, и двигается, и рисуется, и слушает клавиатуру.

Лучше разделять:
- **Entity / SceneObject**: хранит состояние (позиция, размер, теги, компоненты);
- **System**: обрабатывает группы объектов (PhysicsSystem, RenderSystem, InputSystem);
- **Scene**: контейнер объектов + систем + жизненный цикл;
- **Engine**: игровой цикл и переключение сцен.

---

## 2) Рекомендуемая структура пакетов

```text
src/main/java/
  game/
    engine/
      Engine.java              # запуск loop
      GameLoop.java            # fixed update / render
      Time.java                # deltaTime, fixedStep
      scene/
        Scene.java             # интерфейс сцены
        BaseScene.java         # базовая реализация
        SceneManager.java      # загрузка/переключение сцен
      object/
        SceneObject.java       # базовый игровой объект
        Transform.java         # позиция, rotation, scale
        Tag.java               # теги/слои
      component/
        Component.java         # базовый компонент
        SpriteRenderer.java
        Collider2D.java
        Rigidbody2D.java
      system/
        RenderSystem.java
        PhysicsSystem.java
        CollisionSystem.java
        InputSystem.java
      event/
        EventBus.java
      asset/
        AssetManager.java

    gameplay/
      player/
        PlayerObject.java
        PlayerController.java
      world/
        WallObject.java
        PlatformObject.java
      scenes/
        MainMenuScene.java
        TestScene.java

    infrastructure/
      opengl/
        OpenGLRenderer.java
      audio/
        AudioService.java
      io/
        ConfigLoader.java

    debug/
      DebugOverlay.java
      DebugSettings.java
```

Правило простое:
- `engine/*` — универсальные вещи движка;
- `gameplay/*` — конкретно твоя игра;
- `infrastructure/*` — интеграции (OpenGL, звук, файлы);
- `debug/*` — отладка, которая не должна ломать core-архитектуру.

## 3) Базовый `SceneObject`: что в нём должно быть

Если хочешь «создавать любой объект, просто унаследовав от `SceneObject`», делай `SceneObject` минимальным и универсальным.

Минимальный контракт:
- `id` (уникальный идентификатор);
- `name`;
- `transform` (позиция/поворот/масштаб);
- `active`;
- список `components`;
- методы жизненного цикла.

### Жизненный цикл объекта
- `onCreate()` — один раз при создании;
- `onStart()` — когда объект впервые попал в активную сцену;
- `onUpdate(dt)` — логика каждый кадр/тик;
- `onFixedUpdate(step)` — фиксированная физика;
- `onDestroy()` — очистка ресурсов.

> Важно: `SceneObject` **не должен напрямую** читать клавиатуру, рисовать OpenGL и воспроизводить звук одновременно. Это делают системы/компоненты.

---

## 4) Наследование vs композиция (очень важно)

Новичкам кажется, что правильнее «всё через наследование». На практике лучше так:
- **Наследование** — только для базового контракта (`SceneObject` → `PlayerObject`);
- **Композиция (компоненты)** — для фич.

Пример:
- `PlayerObject` + `SpriteRenderer` + `Rigidbody2D` + `Collider2D` + `PlayerInputComponent`.

Тогда для нового объекта не нужно копировать код из `Player`, `Wall`, `Bullet`; ты просто собираешь набор компонентов.

---

## 5) Кто за что отвечает (чеклист ответственности)

### Engine
- цикл `update/fixedUpdate/render`;
- управление временем;
- переключение сцен.

### SceneManager
- загрузить сцену;
- активировать/деактивировать;
- хранить текущую сцену.

### Scene
- хранит объекты и системы;
- знает порядок обновления систем;
- не должен содержать low-level код OpenGL.

### SceneObject
- только состояние + компоненты + lifecycle.

### Systems
- **PhysicsSystem**: интеграция скорости/позиции;
- **CollisionSystem**: пересечения/триггеры;
- **RenderSystem**: отрисовка;
- **InputSystem**: сбор состояния клавиш/мыши.

### Infrastructure
- OpenGL-контекст, загрузка текстур, аудио-движок, сериализация.

## 6) Как добавлять новую фичу без хаоса

Пример: «Хочу прыжок игрока».

1. Добавить данные в `Rigidbody2D` (`velocityY`, `gravityScale`).
2. В `PlayerController` добавить реакцию на кнопку прыжка.
3. В `PhysicsSystem` применить гравитацию/интеграцию.
4. В `CollisionSystem` определить `isGrounded`.
5. Добавить тесты на «прыжок работает только с земли».

То есть фича размазывается по правильным слоям, а не пишется целиком внутри `PlayerObject`.

---

## 7) Минимальный стартовый набор классов (если делать с нуля)

Если перегружен — начни с **очень маленького ядра**:

1. `Engine`
2. `SceneManager`
3. `Scene`
4. `SceneObject`
5. `Transform`
6. `RenderSystem`
7. `PhysicsSystem`
8. `InputSystem`
9. `AssetManager`

Этого уже достаточно, чтобы сделать тестовую сцену с 2–3 объектами и движением.

---

## 8) Практические правила чистого кода для игровых проектов

- Один класс = одна ответственность.
- Не использовать глобальные `static`-состояния для мира игры.
- Не глотать исключения пустыми `catch`.
- Убрать тестовый/экспериментальный код из production-пакетов.
- Все магические числа (`+27`, `0.2`, `-10`) вынести в константы/конфиг.
- Ввод, физика, рендер — разнести по системам.
- На каждую фичу: короткий markdown-док с «какие классы добавлены и зачем».

---

## 9) Как выглядит создание нового объекта в такой архитектуре

Идея:
1. Создаёшь класс `CoinObject extends SceneObject` (минимум кода).
2. Добавляешь компоненты: `SpriteRenderer`, `CircleCollider`, `PickupComponent`.
3. Регистрируешь объект в сцене.
4. Логику подбора обрабатывает `CollisionSystem` + `PickupSystem`.

Плюс: объект создаётся быстро, а код не превращается в «божественный класс».

---

## 10) План миграции твоего текущего проекта (по шагам)

1. Зафиксировать текущий функционал (игрок/платформа/стена).
2. Вынести `SceneObject` + `Transform`.
3. Убрать прямые зависимости объектов от глобальных списков.
4. Ввести `Scene` с собственным списком объектов.
5. Перенести input/physics/render в отдельные системы.
6. Только потом переводить рендер-слой на полноценный OpenGL pipeline.

---

Если коротко: думай не «какой наследник сделать», а «какая ответственность у этого куска кода и в каком слое он должен жить».
